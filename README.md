# Кандидатогенерация для поиска услуг Авито

Решение задачи: для каждого поискового запроса вернуть до 50 объявлений так, чтобы выбранные
пользователем оказались в этом списке. Метрика — **Recall@50**, усреднённая по запросам.

**Результат на лидерборде: 0.8427.**

Данные: 497 673 пары «запрос → выбранное объявление» в обучающей части, корпус из 189 212
объявлений, 2 452 запроса в бенчмарке.

## Анализ данных: почему решение устроено так

Все цифры ниже пересчитаны на своих данных скриптом `scripts/analyze_data.py`, а не взяты из
условия задачи.

| наблюдение | значение | что из этого следует |
|---|---|---|
| объявлений корпуса, встречавшихся в обучающей части | 9.6% | история «этот запрос → это объявление» почти бесполезна: 90% корпуса модель никогда не видела. Обобщать надо через текст, микрокатегорию и параметры |
| запросов бенчмарка, встречавшихся в обучении | 37.5% | две трети запросов новые, память по запросам не поможет |
| пар обучения, где локация поиска совпала с локацией объявления | 83.1% | гео — сильнейший сигнал после текста |
| запросов бенчмарка, у которых в своей локации нет ни одного объявления | 17.4% | жёстко фильтровать по `location_id` нельзя: каждый шестой запрос остался бы без выдачи. Только расстояние до центра локации |
| объявлений с неуникальным заголовком | 44.5% | заголовка недостаточно, чтобы отличить объявление от соседнего. Нужны описание и параметры, то есть BM25F по полям |
| выборов, попавших в доминирующую микрокатегорию запроса | 86.3% | запрос почти однозначно задаёт микрокатегорию — значит `P(microcat \| запрос)` стоит обучить отдельно и отдать ранкеру |

Расстояние от выбранного объявления до центра локации запроса: медиана 3.2 км, 75-й процентиль
7.6 км, 90-й — 16.8 км, 95-й — 38 км, 99-й — 793 км. Отсюда две вещи: окрестность имеет смысл
брать небольшой, но у нескольких процентов услуг (онлайн, выездные) объявление может быть в другом
регионе — поэтому радиус работает как приоритет, а не как отсечение.

## Устройство решения

```
запрос → BM25F по 6 полям → пул кандидатов (2 гео-канала) → LightGBM lambdarank → top-50
```

1. **Поля документа.** Заголовок; `kind` / `service` / `place` / `other`, полученные разбором
   плоской строки параметров; полное описание объявления. Разбор параметров — `src/params.py`,
   список ключей добывается скриптом `scripts/discover_param_keys.py`.
2. **BM25F** с весами `title 3, kind 2, service 2, place 0.5, other 0.3, desc 1` и разной
   нормировкой длины по полям: короткий точный заголовок нормируется слабо (`b=0.3`), рыхлое
   описание — сильно (`b=0.9`).
3. **Пул кандидатов** — объединение двух каналов по 600 мест: жёсткий приоритет радиуса 30 км
   (лучше для точности) и мягкий штраф `−log(1+dist)` (лучше для полноты). Ранги в каждом канале
   идут в признаки ранкера.
4. **Ранкер** LightGBM `lambdarank`, 32 признака: BM25F суммарно и по каждому полю, ранги обоих
   гео-каналов, расстояние и флаги радиусов, `P(microcat | запрос)`, популярность объявления,
   отзывы, рейтинг, цена, плотность окрестности и относительные величины внутри события.

## Что дало прирост

| система | R@50 на валидации |
|---|---|
| BM25 (заголовок + сырые параметры) + приоритет радиуса 80 км | 0.690 |
| то же, радиус 30 км | 0.705 |
| BM25F по полям + **полное описание объявления** | 0.831 |
| + гибридное гео (радиус 50 км и штраф за расстояние) | 0.839 |
| **+ пул из двух каналов и ранкер** | **0.918** |

Основной вклад — описание объявления как отдельное поле BM25F: около **+0.11 R@50**. Обрезать его
не нужно, качество растёт монотонно до полного текста (200 → 400 → 800 → 1600 символов → полностью
даёт 0.767 → 0.784 → 0.805 → 0.823 → 0.831).

## Анализ ошибок

### Куда девались позитивы у точки отсчёта

Для каждого выбранного объявления посчитано, почему оно не попало в top-50 у точки отсчёта
(BM25 по заголовку и сырым параметрам, приоритет радиуса 80 км). Причины взаимоисключающие,
сумма даёт все 3383 позитива валидации.

| причина | доля позитивов | чем закрыто |
|---|---|---|
| попали в top-50 | 75.6% | — |
| в пуле top-1000, но ниже 50-го места | 13.0% | ранкер: переупорядочивание пула, +0.09 R@50 |
| нет ни одной общей леммы с запросом | 5.4% | описание объявления как поле BM25F, +0.11 R@50 |
| объявление дальше 80 км | 4.2% | второй канал пула с мягким штрафом за расстояние вместо отсечения |
| не попали даже в top-1000 | 1.8% | объединение двух каналов, потолок пула вырос до 0.969 |

Самая крупная статья — не отсутствие кандидата, а его неверное место в выдаче. Поэтому основные
силы ушли в ранкер и в качество текстовых признаков, а не в расширение пула.

Доля позитивов в top-50 (75.6%) выше, чем R@50 точки отсчёта (0.690), потому что метрика
усредняется по событиям: событие с одним пропущенным позитивом даёт ноль целиком.

### Где теряем сейчас

Качество сильно зависит от того, насколько плотная локация у запроса:

| объявлений в окрестности 30 км | R@50 |
|---|---|
| меньше 659 | 0.935 |
| около 3 300 | 0.926 |
| больше 27 000 | 0.825 |

Разрыв 0.11. В крупных городах десятки кандидатов содержат те же слова запроса и стоят рядом по
BM25 — различить их лексикой уже нельзя.

### Расхождение валидации и лидерборда

На валидации 0.918, на лидерборде 0.843. Разрыв 0.075 разобран, и **причина не найдена** — ниже
то, что проверено и отвергнуто, чтобы не проверять это повторно.

| версия | как проверялась | вклад в разрыв |
|---|---|---|
| утечка: признаки видят те же события, на которых считается метрика | аудит пересечений событий и запросов между обучающей частью и валидацией | 0 |
| вставка позитивов в корпус облегчает задачу | R@50 на событиях, чьи позитивы и так были в корпусе бенчмарка: 0.920, то есть выше общей | 0 |
| признаки на бенчмарке распределены иначе | сравнение пула бенчмарка с пулом валидации: сдвиги медиан не больше 0.11 стандартного отклонения | 0 |
| в валидации позитив конкурирует с объявлениями другого происхождения | пересборка корпуса целиком из обучающей части: 0.906 против 0.909 | 0.003 |
| позитивы валидации чаще встречались в обучении, чем случайное объявление | перевзвешивание под состав бенчмарка | не больше 0.009 |
| у бенчмарка другое распределение плотности локаций | перевзвешивание валидации по плотности | 0 |
| у бенчмарка больше выбранных объявлений на запрос | R@50 только на событиях с одним позитивом: 0.908 против 0.909 | 0 |

Остаток — различие между событиями обучающей части и запросами бенчмарка, которое из обучающих
данных не воспроизводится. Практический вывод: абсолютную цифру валидации надо читать со сдвигом,
а сравнения конфигураций между собой остаются осмысленными.

### Что пробовал и что не сработало

Сравнения в этом разделе шли на пуле из 600 кандидатов — он считается быстрее. База: **0.906** на
сиде 42 и **0.908** в среднем по трём сидам (у финального решения на пуле 1200 — 0.918). Знак и
величина разницы от размера пула не зависят.

| попытка | результат |
|---|---|
| обучить ранкер на 30 000 событиях обучающей части вместо 3 000 валидационных | 0.891 против 0.908 в среднем по трём сидам; хуже на каждом сиде и во всех вариантах набора признаков |
| поднять `lambdarank_truncation_level` с 30 до 50–400 под метрику Recall@50 | разброс 0.002 на сиде 42, дефолт оказался не хуже |
| бинарная классификация вместо попарной функции потерь | 0.899 против 0.906 на сиде 42 |
| признаки текстового совпадения: покрытие запроса полем, длина общей подпоследовательности, близость слов, позиция первого совпадения | −0.0002 |
| признаки выдачи: однородность скоров, доля кандидатов нужной микрокатегории | −0.0019 |
| адаптивная окрестность: K ближайших объявлений вместо радиуса | до −0.19; в плотных локациях 0.17, потому что K ближайших в крупном городе сжимаются в пару километров |
| третий канал пула по квантилю расстояний внутри микрокатегории | потолок пула 0.945 против 0.954: при фиксированном размере пула каналы отнимают места друг у друга |

Причина в том, что ранкер достаёт 95% позитивов, которые уже лежат в пуле (0.906 из потолка 0.954).
Добавлять признаки из семейства «лексика + гео + микрокатегория» больше нечего, оно исчерпано.

### Что стоит попробовать дальше

Дообученный на парах обучающей части dense-энкодер: косинус «запрос — объявление» и как признак
ранкера, и как отдельный канал пула. Это единственный принципиально другой источник сигнала —
семантика вместо совпадения слов, — и он бьёт именно в плотные локации, где лексика бессильна.

## Валидация и метрики

Лидерборд для подбора не используется — попыток мало. Судит локальная валидация, повторяющая
устройство бенчмарка: 3000 событий, из них 62.5% с запросом, полностью удалённым из обучения
(«unseen»), и 37.5% с одним удалённым событием («seen») — ровно те доли, что в бенчмарке. Корпус
валидации = корпус бенчмарка плюс позитивы валидации; доля объявлений, знакомых обучающей части,
получается 9.9% против 9.6% на бенчмарке.

Все статистики, словари и модели строятся только по маске `fit_mask`. Проверка на утечку выполняется
при каждом построении сплита.

Что смотрели:

* **R@50** — целевая метрика;
* **R@200 и R@1000** — состав пула, потолок, выше которого ранкер не поднимется;
* **разбивка R@50 на seen/unseen** — чтобы прирост не оказался «историей по запросу», которой
  на бенчмарке не будет. У финального решения R@50 = 0.930 на seen и 0.910 на unseen (среднее по
  трём сидам): разрыв всего 0.02, то есть решение работает и на незнакомых запросах;
* **top-k точность классификатора микрокатегорий** (top-1 0.694, top-5 0.920);
* **важность признаков ранкера** — какие сигналы он реально использует;
* **разброс итога по трём сидам** валидационного сплита: 0.9167 / 0.9178 / 0.9186.

## Запуск

```bash
uv venv --python 3.12 .venv
VIRTUAL_ENV=.venv uv pip install -r requirements.txt
# положить train.parquet, benchmark_items.parquet, benchmark_queries.parquet в data/
make answer
```

`make answer` строит `results/answer.csv` — около 4 минут: валидационный сплит, классификатор
микрокатегорий, пул кандидатов и финальный прогон по бенчмарку. Пик памяти ~3 ГБ.

`make all` дополнительно прогоняет шаги подбора (точка отсчёта, длина описания, гео-режимы) и
ранкер на трёх сидах — около 25 минут, пик памяти ~12 ГБ из-за матрицы расстояний 3000 × 192 000.
Отдельные шаги: `make baseline`, `make text`, `make geo`, `make ranker`, `make verify`.

Ноутбук `notebooks/solution.ipynb` проходит весь путь с метриками на каждом шаге и в конце сверяет
полученный файл с отправленным по контрольной сумме.

## Структура

```
src/
  paths.py      пути проекта
  text.py       нормализация запросов, лемматизация с кэшем токенов
  params.py     разбор строки параметров объявления в поля
  data.py       чтение parquet (decimal128 → float, выборочные колонки)
  corpus.py     сборка и кэширование лемматизированных полей
  bm25.py       BM25 и BM25F, подбор весов без пересборки индекса
  geo.py        центры локаций поиска, haversine
  microcat.py   классификатор P(microcat | запрос)
  metrics.py    Recall@K с усреднением по событиям
scripts/
  build_val.py            валидационный сплит
  discover_param_keys.py  инвентарь ключей параметров
  analyze_data.py         свойства данных и таксономия промахов
  eval_bm25_baseline.py   точка отсчёта: BM25 + гео-режимы
  eval_desc.py            вклад описания, подбор длины
  eval_geo.py             сравнение гео-режимов
  train_microcat.py       классификатор микрокатегорий
  build_pool.py           пул кандидатов с признаками
  train_ranker.py         ранкер, кросс-валидация по событиям
  verify_seeds.py         проверка на нескольких сидах
  predict_ranker.py       финальный прогон и answer.csv
notebooks/solution.ipynb  весь путь решения с метриками
results/answer.csv        отправленный файл
```

## Зависимости

Python 3.12, всё считается на CPU. Внешние обученные модели не используются.

| библиотека | лицензия | зачем |
|---|---|---|
| numpy, scipy | BSD-3 | разреженная алгебра, BM25 через матричное умножение |
| pandas, pyarrow | BSD-3 / Apache-2.0 | чтение parquet, агрегации |
| scikit-learn | BSD-3 | векторизация текста, наивный байес |
| pymorphy3 + pymorphy3-dicts-ru | MIT / LGPL-2.1 | лемматизация русского |
| lightgbm | MIT | ранкер |

Версии закреплены в `requirements.txt`. Сиды фиксированы: сид валидационного сплита задаётся
флагом `--seed`, внутри моделей `random_state=0`.
